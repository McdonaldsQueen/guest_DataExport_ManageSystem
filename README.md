# 嘉宾名单核对、统计与导出工作台

**guest_DataExport_ManageSystem · v0.1.0**

面向招商大会嘉宾组的单人工作台原型：查看参会单位与嘉宾、集中核对缺失信息、试算邀请进展、生成Excel名单和Word汇报核对稿。

本仓库保存可以独立运行的前端代码和**完全虚构的演示数据**。真实企业、嘉宾名单、联系人、原始Excel及业务核对个案不包含在公开仓库中。

**当前可用的私有工作台：**

https://sz-investment-workbench-kk.folksywand2.chatgpt.site

该地址的访问权限由托管平台控制，仅授权账号可访问。GitHub仓库公开不代表这个私有工作台公开。仓库另提供GitHub Pages公开演示部署：首次需要在仓库Settings → Pages中将来源设为GitHub Actions；随后main分支的应用文件更新会自动部署。是否上线以部署工作流成功记录为准。

## 1. 项目背景与目标

大会邀请名单通常由多个区、市直单位、业务处室分别填报。每日汇总时，常见问题包括：

- 同一企业使用简称、集团名、法人名等多种名称。
- 同一嘉宾被多个部门重复邀请，职务表述不同。
- 参会状态有“是、否、待定、空白”，需要披露不同口径。
- 单位已确认参会，但具体人选、职务、国籍尚未补齐。
- 企业性质、行业、国别存在冲突。
- 全市去重总数与部门成果加总不一致。
- 名单、重点嘉宾表、部门KPI和Word汇报需要来自同一份处理结果。

工作台第一版主要承接**已经完成上游清洗、归并、去重及人工确认的名单快照**，提供可操作的查看、核对和输出界面。

它不是完整的会议报名系统，也不是通用在线Excel。原始表处理服务、多人协作和正式批次发布将在后续迭代中接入。

## 3. 快速启动

### 3.1 环境要求

- Node.js **20或以上**；自动检查使用Node.js 22。
- 现代桌面浏览器，建议先使用最新版Chrome或Edge。
- Python 3只用于可选的Office文件结构检查，不是启动页面的必需条件。
- 无需数据库、API Key或第三方账号。
- 无运行时npm依赖，无需执行 `npm install`。

### 3.2 克隆与运行

```bash
git clone https://github.com/McdonaldsQueen/guest_DataExport_ManageSystem.git
cd guest_DataExport_ManageSystem
npm run dev
```

浏览器打开：

```text
http://127.0.0.1:4173
```

`npm start` 与 `npm run dev` 行为相同。服务器默认只监听本机，按 `Ctrl+C` 停止。

### 3.3 Windows PowerShell自定义端口

```powershell
$env:PORT = "4180"
npm run dev
```

需要在可信局域网中测试时可设置 `HOST=0.0.0.0`，但这不提供登录或访问权限。真实数据环境应使用有访问控制的部署方式。

### 3.4 直接使用Python启动

```bash
python -m http.server 4173 --bind 127.0.0.1 --directory dist
```

不要直接双击 `dist/index.html`：页面默认通过HTTP读取同目录的 `data.json`，`file://` 下浏览器可能拦截读取。

### 3.5 构建

```bash
npm run build
```

本项目没有编译打包步骤。该命令检查静态文件、JavaScript语法、数据基本结构与稳定id。**实际发布目录就是 `dist/`。**

## 4. 页面与操作流程

### 4.1 工作总览

显示当前内存数据下的确认单位、嘉宾、重点标签数量和嘉宾资料不全数量。下方展示各区成果、企业行业分布及当前草稿状态。

如果存在本机修改，顶部会出现草稿提示。此时数字是本机试算，不能直接当作已发布的正式统计批次。

### 4.2 数据导入

1. 选择 `.xlsx` 文件。
2. 在工作表按钮中切换查看。
3. 检查工作表、表头与示例数据。
4. 确认该文件是否符合后续处理要求。

**当前上传到此结束。**上传不修改 `dist/data.json`，不自动归并企业，不自动发布新名单。预览最多读取每张表前5001行，界面展示选中表的前15条数据、最多8列；首行直接作为预览表头，尚无多行表头自动识别。

### 4.3 信息核对

可筛选参会状态待确认、人选未落实、职务缺失、国籍缺失和单位资料问题。

打开一条记录后：

1. 查看邀请责任单位、原始行号和原姓名/职务。
2. 编辑嘉宾姓名、职务、国籍或参会状态。
3. 填写“核对依据/说明”。
4. 保存为本机草稿。
5. 返回总览或邀请进展查看试算结果。

“仅标记已查看”不会补齐字段，也不会把问题当作已解决。还可以恢复单条原始数据。

### 4.4 参会单位

默认展示确认口径中的全部单位。支持企业、招商合作机构、资料待完善筛选。单位详情内可以查看所属嘉宾并进入核对。

每家单位以稳定 `id` 识别，显示名不会自动成为合并依据。

### 4.5 参会嘉宾

默认只展示参会状态为“是”的记录。可筛选重点标签、高管标签、资料不全记录。

重点及高管是已经核定的标签；修改职务后标签不会自动变化。需要重新执行上游筛选后更新正式快照。

### 4.6 邀请进展

切换各区与市直单位，显示任务指标、确认单位数、其中企业数、确认嘉宾数和完成率。默认按确认单位数降序，支持切换升序。

### 4.7 文件输出

生成当前内存数据的独立名单、问题表、Word核对稿。存在草稿时，导出会包含本机修改。Word中会注明是否为草稿试算。

### 4.8 统计规则

查看快照中的规则文件并另存。第一版不支持在线修改统计规则，也不把自然语言规则自动执行为程序。

## 5. 统计口径

### 5.1 参会状态

| 状态 | 确认参会 | 暂计展示 | 说明 |
| --- | --- | --- | --- |
| 是 | 计入 | — | 包含已确认但人选未落实的名额 |
| 待定 | 不计入明确确认数 | 单列 | 上游可按业务规则纳入含暂计总数 |
| 空白 | 不计入明确确认数 | 单列 | 有效记录与纯空行识别由上游完成 |
| 否 | 不计入 | 不计入 | 当前不参会 |

确认参会嘉宾数＝`status === "是"` 的嘉宾/名额记录数。当前界面不是通过姓名是否填全来决定是否确认参会。

### 5.2 单位与嘉宾去重

- 确认单位：确认嘉宾记录对应的 `unitId` 去重。
- 确认嘉宾：输入快照中的稳定嘉宾/名额记录，前端不再次进行姓名相似匹配。
- 一个企业多名嘉宾：单位1家、嘉宾分别计数。
- 一个嘉宾多个邀请来源：全市只计一条，各邀请责任单位分别计成果。
- 不同独立主体是否同集团、是否合并为一家，由上游业务规则决定。

### 5.3 企业与机构

`type === "意向投资企业"` 计入企业；`type === "招商合作机构"` 计入机构；其他值保留待核对。确认单位总数可大于企业数。

企业性质使用 `primaryNature` 唯一主分类。优先级最小编号应由上游确定。前端不核验企业榜单，也不根据注册地单独判断内外资。

### 5.4 资料不全

嘉宾任一关键字段姓名、职务、国籍存在缺失或待定/未知标记，计入嘉宾资料问题。同一记录多个问题只计一次合计。单位国别、类型、行业及适用性质字段另行检查。

`guestIssues()` 与 `unitIssues()` 是本机校验入口；它们是明确的字段检查，不是AI事实核验。

### 5.5 部门成果与KPI

```text
部门确认单位数 = 该部门邀请的确认记录所对应unitId去重数
部门确认嘉宾数 = 该部门邀请的确认嘉宾/名额记录数
完成率 = 部门确认单位数 ÷ 任务指标 × 100%
```

目前KPI分子包含企业和机构，企业数另列。若业务要求只考核企业，需要明确调整分子与页面命名，不应只替换表头。

各区演示配置：大鹏新区、深汕特别合作区50家，其他所列区级责任单位100家。市直指标保存在 `departments`，可以随业务任务版本调整。

**部门成果加总与全市去重总数不同，不能混用。**

### 5.6 重点嘉宾与高管

本版消费预先核定的 `priority`、`senior` 布尔标签。业务筛选方向为榜单与职务、未上榜企业高职级、机构正职负责人，但判断逻辑尚未在本前端执行。不能把修改职务后保留的标签当作重新核定结果。

## 6. 数据模型与接口

完整字段说明、单位及嘉宾JSON示例、来源字段限制，见 [docs/DATA_CONTRACT.md](docs/DATA_CONTRACT.md)。

| 对象 | 核心字段 | 用途 |
| --- | --- | --- |
| 单位 | id、name、short、type、primaryNature、institution、industry | 名称、分类与单位归属 |
| 嘉宾/名额 | id、unitId、name、title、nationality、status | 参会与个人字段 |
| 邀请来源 | guests[].owners | 多部门成果归属 |
| 原始来源 | lines | 原始行号；完整文件/工作表来源键待扩展 |
| 任务指标 | departments[].label、target | KPI配置 |
| 规则说明 | rules[].name、text | 已确认口径的说明文本 |
| 快照基线 | baseline | 日期和核定计数 |

修改数据后运行测试。修改快照不能只改 `baseline` 数字，必须保持底层记录、关联和人数一致。

### 当前技术栈

- 原生HTML、CSS、JavaScript。
- Hash路由，无服务端路由重写要求。
- `fetch` 读取静态JSON快照。
- `localStorage` 保存浏览器草稿。
- 浏览器 `Blob`、`TextEncoder`、`DOMParser`、`DecompressionStream` 处理文件。
- Node.js仅用于本地服务和检查。

**当前没有使用React、Next.js、TanStack Table、Python API服务或数据库。**这些是此前讨论过的后续技术方向，不应与已经交付的第一版混淆。

### 数据流

```text
已处理名单快照 → 页面加载 → 筛选/统计/核对草稿 → 本机试算 → 文件导出

新原始Excel → 浏览器预览 → 等待后续后台处理与批次发布功能
```

## 8. 文件导出与导入

### 8.1 Excel导出

通过 `office.js` 生成Office Open XML `.xlsx`，使用不压缩ZIP封装，字符串转义和XML结构由代码构造。没有把CSV改后缀伪装成Excel。

嘉宾、重点嘉宾、高管明细统一五列：

1. 企业全称
2. 企业简称
3. 企业类型
4. 嘉宾姓名
5. 嘉宾职务

单位名单、问题清单、部门进展按各自用途输出字段。导出保留原本缺失信息，不虚构补齐。每次生成单独文件，不自动上传或发送给其他人。

### 8.2 Word导出

输出真实 `.docx`，包括总体情况、嘉宾信息、资料完善及各责任单位进展。使用简单段落结构，便于打开后继续编辑。

它不是现有机关Word模板的完整格式复刻；标题层级、表格、页眉页脚、附件编号和最终公文排版尚未模板化。导出仍应人工审阅。

### 8.3 Excel预览

- 只支持 `.xlsx`，不支持老式 `.xls`、加密文件或宏运行。
- 文件限制20MB；单个XML条目声明解压体积限制40MB。
- 使用浏览器原生解压API，需要支持 `DecompressionStream('deflate-raw')`。
- 不运行Excel公式，不做格式完整还原；公式单元格依赖已有缓存值。
- 不上传到后台、不自动存档、不替换快照。
- 这不是面向任意不可信文件的生产级解析服务；正式化时应增加资源限制与独立解析验证。

## 9. 核对草稿与数据版本

### 9.1 保存内容

浏览器保存编辑字段、核对说明、已查看标记和本机事件记录。存储键为：

```text
sz-investment-workbench-v1
```

页面刷新时尝试重新加载。隐私模式、浏览器策略、清理站点数据或换设备均可能导致草稿不可用。

### 9.2 导出草稿

信息核对页及草稿提示区可导出JSON，作为手工保存副本。当前没有“导入草稿JSON”的界面，也没有自动云端备份。

### 9.3 当前版本限制

- 草稿不等于已发布的正式名单。
- 日志不是不可篡改审计凭证。
- 恢复单条记录会恢复字段，历史本机事件仍可能保留。
- 新快照未实现批次隔离。更换数据前必须处理旧草稿，防止相同id套用旧修改。
- 修改参会状态会改变本机统计；修改职务不会自动重新识别高管或重点。

## 10. 检查与验收

### 10.1 自动检查

```bash
npm test
python scripts/check_office.py
```

检查内容：

- 静态文件和JavaScript语法。
- 单位id唯一、嘉宾id唯一、单位引用有效、状态值合法。
- 确认单位、嘉宾、重点、高管计数与快照基线一致。
- 八个页面的函数渲染冒烟检查。
- 搜索结果、缺失信息补齐后的校验、状态变化后的人数试算。
- XLSX和DOCX字节生成。
- ZIP CRC和XML可解析性。

测试文件写入 `qa/`，该目录已忽略，不上传业务导出文件。

自动检查使用模拟DOM，**不覆盖真实浏览器点击、视觉布局、上传解析及桌面Excel/Word行为**。可解析不等于已证明所有Office版本无需修复。

### 10.2 手工验收建议

## 11. 部署说明

### 11.1 已上线私有版本

地址见README开头。私有版接入私有业务快照，访问权限由托管平台提供。当前仓库与该托管源是**两个独立的代码同步目标**，推送GitHub不会自动更新私有站点。

这一区分是为了让公开源代码与真实业务数据分开。后续可建设受控的构建流水线，但不要把私有快照提交进公开Git历史。

### 11.2 其他静态托管

本项目可以部署到支持静态文件的服务：

```text
发布目录：dist
构建命令：npm run build（校验，无编译）
启动入口：index.html
```

资源采用相对路径，页面通过Hash导航，适合子路径部署。不需要SPA路径重写。

真实业务快照被浏览器加载后，授权访问者可以读取它；隐藏按钮不是数据权限。需要私有访问时，应先配置主机层访问控制或后端认证，再放入真实数据。

### 11.3 GitHub Pages公开演示

仓库已提供部署工作流 `.github/workflows/deploy-pages.yml`，支持main分支应用文件变更自动触发，以及手动触发。

操作步骤：

1. 进入仓库 `Settings → Pages`。
2. 将构建发布来源设为 `GitHub Actions`。
3. 确认 `dist/data.json` 仍为虚构演示数据。
4. 进入 `Actions → Deploy public demo to GitHub Pages`。
5. 点击 `Run workflow`，选择 `main`。
6. 等待部署完成，使用工作流环境输出的实际地址访问。

首次启用后，main分支的dist、scripts、tests、package.json或部署工作流发生变化会自动发布。部署前会检查baseline.mode必须为demo。该标记只是防误操作，不能代替检查数据内容。未完成仓库Pages设置时，工作流会报配置错误；添加工作流文件本身不代表Pages已上线。

### 11.4 自动检查

`validate.yml` 在main分支推送和PR时运行测试，不部署站点。GitHub Actions需要在仓库设置中启用；平台是否实际执行应以Actions记录为准。

## 12. 接入真实数据

建议顺序：

1. 在私有环境整理原始Excel、榜单和人工确认结果。
2. 使用业务处理程序清洗、归并、去重，并保留来源。
3. 按数据接口生成完整快照。
4. 核对总数、分类合计、未知项、部门成果及明细。
5. 处理旧浏览器草稿与id映射。
6. 在访问受控的环境更新快照并测试。
7. 人工核定后输出正式名单和公文。

本公开仓库没有附带原始业务处理脚本：它们依赖内部源文件、榜单和人工个案，不能把此处“上传预览”理解为已经实现该链路。

`.gitignore` 忽略常见原始文件和私有目录，但**不会阻止误把真实内容写入已跟踪的 `dist/data.json`**。提交前必须审查文件和暂存区。

## 14. 常见问题

**为什么上传Excel后统计不变？**

因为上传功能仅用于预览。完整处理与正式快照更新尚未接入。

**为什么部门成果之和大于全市总数？**

同一单位或嘉宾可由多个部门共同邀请，各部门分别计成果；全市总数需要跨部门去重。

**姓名待定为什么还在确认嘉宾中？**

参会状态和人选落实是两项信息。当前业务口径允许状态为“是”的待定名额计入，并单列资料问题。

**修改职务后为什么仍然在高管/重点名单？**

标签来自原快照，前端未重新执行筛选。需要上游核定后更新。

**核对草稿为什么换电脑后不见了？**

因为保存在浏览器本地，没有账号同步服务。可先导出JSON保留副本。

**能否直接用公开GitHub Pages放真实名单？**

该仓库的Pages工作流用于虚构演示。真实名单应部署到访问受控的环境，不能用前端隐藏内容代替权限。

**Excel或Word提示修复怎么办？**

保留原导出文件和Office修复日志，记录浏览器及Office版本，再定位文件结构问题。仓库测试只验证ZIP/XML等结构，不代表所有桌面版本兼容性已覆盖。

**为什么公开演示数字与私有工作台不同？**

公开仓库使用虚构24家/36人快照；私有站点使用独立业务快照。两者不应混为同一批次。
